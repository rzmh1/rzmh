# خطة إعادة تطوير رُزمة الشاملة — تعليمات Codex

> الحالة: خطة تنفيذ على فرع تجريبي فقط. لا تدمج إلى main ولا تنشر على Northflank قبل موافقة مالك المشروع الصريحة.

## الهدف

إعادة تطوير تجربة رُزمة بالكامل بتصميم تعليمي فاخر وحديث، مع تنظيف المحتوى والواجهات، والحفاظ التام على الحسابات والاشتراكات والنتائج وسجلات تقدم الطلاب والطلبات والإعدادات والملفات. لا تبدأ من الصفر ولا تستبدل قاعدة البيانات أو مخططها دون ترحيل آمن ومتوافق.

## قواعد غير قابلة للتفاوض

1. اعمل حصراً على الفرع `codex/ruzmah-full-redesign`. لا تكتب إلى `main` ولا تنفذ merge أو deploy أو release.
2. لا تغيّر إعدادات Northflank ولا أسرار البيئة ولا متغيرات الإنتاج.
3. لا تحذف قاعدة البيانات أو ملفات المستخدمين أو التخزين الدائم، ولا تنفذ reset أو seed على بيانات حقيقية.
4. قبل أي تغيير في schema، أنشئ migration إضافية قابلة للترقية، واختبرها على نسخة اختبارية من قاعدة بيانات منزوعة البيانات الشخصية. لا تنفذ migration على الإنتاج.
5. لا تكشف أو تطبع API keys أو كلمات المرور أو session tokens أو بيانات شخصية. لا تضع أسراراً في Git.
6. حافظ على توافق API والبيانات قدر الإمكان. أي تغيير غير متوافق يحتاج migration موثقة وخطة rollback.
7. لا تدّع نجاح اختبار لم يتم تشغيله. سجّل الأوامر والنتائج الفعلية.
8. لا تستخدم بيانات طلاب حقيقية في لقطات الشاشة أو fixtures أو الاختبارات.
9. لا تضف خدمات مدفوعة أو اشتراكات جديدة دون موافقة المالك.
10. لا تحذف أي ميزة موجودة لمجرد إعادة التصميم. أصلحها أو وثّق سبب اقتراح إزالتها وانتظر الموافقة.
11. لا تنتقل إلى تنفيذ تغييرات المنتج أو إعادة التصميم قبل تقديم معاينات مرئية كاملة والحصول على موافقة المالك عليها.
12. لا تستخدم الإنترنت أو مصادر خارجية أو المعرفة العامة لتزويد الطالب بمحتوى تعليمي، إلا إذا غيّر المالك هذه السياسة لاحقاً صراحة. المصدر التعليمي المعتمد هو محتوى رُزمة المنشور والمصرح به فقط.

## المرحلة 0 — جرد وفهم قبل التعديل

- اقرأ README وpackage.json وجميع وثائق المشروع.
- ارسم خريطة الصفحات ومسارات الطالب والزائر والمالك وواجهات API.
- وثّق الأدوار والصلاحيات، تدفق تسجيل الدخول، الاشتراكات والدفع، الاختبارات والنتائج، التخزين، الذكاء الاصطناعي، النسخ الاحتياطي.
- حدد الملفات القديمة والمكررة والميزات غير المستخدمة، لكن لا تحذفها في هذه المرحلة.
- شغّل الاختبارات الحالية وbuild وlint إن وجدت، وسجّل baseline كما هو.
- افحص إعدادات النشر لمعرفة هل Northflank يبني من main أو فرع آخر؛ لا تغير الإعداد.
- أخرج `docs/REDESIGN_AUDIT.md` وفيه: الموجود فعلاً، الناقص، المخاطر، ونتائج الاختبارات.

**بوابة موافقة:** لا تبدأ تغييرات واسعة قبل إنهاء الجرد وتقديم ملخص audit.

## المرحلة 1 — معاينة التصميم قبل التنفيذ (إلزامية)

هذه المرحلة تسبق إعادة بناء الصفحات والوظائف. المطلوب أن يستطيع المالك رؤية الشكل الجديد كاملاً قبل الموافقة على تنفيذه.

- اعرض مقترحين أو ثلاثة لاتجاه بصري متناسق، ثم اختر الاتجاه الفاخر الحديث بعد توضيح الفروقات.
- جهّز نماذج مرئية عالية الدقة للصفحات الأساسية: الصفحة الرئيسية/المتجر، تسجيل الدخول، تهيئة الطالب الجديد، لوحة الطالب، صفحة المادة/الدورة، الدرس، الاختبار، نتيجة الاختبار، المدرّس الذكي مع الصورة والسبورة، مكتبة المعرفة، ولوحة المالك وأهم صفحات إدارتها.
- اعرض حالات الجوال والكمبيوتر، وليس سطح المكتب فقط.
- عاين الألوان والخطوط والأيقونات والأزرار والبطاقات والجداول والقوائم والنوافذ والحالات الفارغة والتحميل والخطأ والنجاح.
- اعرض تدفقات تفاعلية أو نموذجاً قابلاً للنقر للرحلات الرئيسية، مع بيانات تجريبية فقط.
- لا تربط المعاينة بقاعدة الإنتاج ولا بمفاتيح الإنتاج ولا ترسل رسائل أو مدفوعات حقيقية.
- قدّم للمالك رابط معاينة آمن أو صوراً واضحة مع تقرير الفروقات. لا تعتبر لقطة واحدة للصفحة الرئيسية معاينة كافية.
- انتظر موافقة المالك على التصميم والواجهات والتدفقات قبل بدء إعادة التنفيذ الشاملة. سجّل التعديلات المطلوبة أولاً.

## المرحلة 2 — أساس التصميم وتجربة الاستخدام

أنشئ نظام تصميم موحداً:
- هوية عربية RTL صحيحة، خطوط واضحة، تباين وأحجام مقروءة.
- تصميم فاخر وحديث وهادئ، أنيق ومميز، لا ازدحام ولا زخرفة زائدة.
- راجع لوحة الألوان والتدرجات والخلفيات والحدود والظلال، واختر ألواناً مريحة ومتناسقة مع هوية رُزمة.
- حسّن الأزرار: التسلسل البصري، الحجم، حالات hover/focus/disabled/loading، وعدم وجود أزرار متشابهة لأفعال مختلفة.
- حسّن البطاقات: المسافات، العناوين، الأوصاف، الأيقونات، إبراز الإجراء الأساسي، وتوحيد الارتفاعات عند الحاجة.
- مكونات موحدة للحقول والجداول والنوافذ والتنبيهات والحالات الفارغة.
- دعم responsive حقيقي للجوال واللوحي وسطح المكتب.
- حالات loading / empty / error / success لكل عملية مهمة.
- تنقل واضح، عناوين مفهومة، عدم إخفاء الإجراءات الأساسية داخل قوائم غير بديهية.
- إمكانية الوصول: لوحة مفاتيح، focus واضح، labels، تباين، ورسائل أخطاء مفهومة.

لا تغيّر قواعد الأعمال أثناء إعادة تصميم الواجهة.

## المرحلة 3 — رحلة الطالب

صمّم رحلة تهيئة أول دخول:
1. اختيار المسار: قدرات، تحصيلي، STEP.
2. موعد الاختبار إن وجد.
3. تحديد المستوى أو اختبار تشخيصي اختياري.
4. وقت المذاكرة المتاح.
5. اختيار المدرسين/المصادر/الدورات المنشورة داخل رُزمة فقط.
6. إنشاء خطة أولية قابلة للتعديل.

لوحة الطالب الرئيسية يجب أن تجيب بوضوح: ماذا أذاكر اليوم؟ ما التالي؟ ما تقدمي؟ ما نقاط ضعفي؟ ما الاختبار القادم؟
- اربط الدروس والاختبارات والأخطاء بالخطة.
- عند الخطأ، اعرض تفسيراً ومصدر تعلم من رُزمة وتدريباً علاجياً من بنك رُزمة.
- اعرض تقدم الطالب بصدق ولا تعرض أرقاماً وهمية.
- حافظ على السجل السابق والنتائج والاشتراكات.

## المرحلة 4 — المحتوى وبنك الأسئلة

صمّم سير عمل آمن لإضافة المحتوى:
- إدخال يدوي، CSV/XLSX، وPDF/DOCX عند دعم الاستخراج.
- استخراج الأسئلة والخيارات والإجابة والتفسير والموضوع والمستوى.
- واجهة مراجعة بشرية قبل نشر أي سؤال مستخرج أو مولد.
- تمييز مصدر السؤال: ملف أصلي، إدخال يدوي، أو مولد AI.
- منع التكرار قدر الإمكان، والتحقق من صحة عدد الخيارات والإجابة.
- دعم الوسوم: المسار، القسم، الموضوع، المهارة، الصعوبة، المدرس، مصدر المحتوى.
- حفظ مسودات، نشر، إلغاء نشر، وأرشفة دون حذف نتائج الطلاب السابقة.
- لا تنسخ أو تعيد نشر مواد مدفوعة أو محمية بحقوق دون تصريح من مالكها.
- لا تجعل المدرّس يستند إلى اسم مدرس أو دورة أو ملف غير موجود فعلياً في مكتبة رُزمة المنشورة والمصرح بها.

## المرحلة 5 — المدرّس الذكي: الصور ومصادر المعرفة والسبورة الذكية

### أ. نطاق المدرّس والمواد المسموح بها

المدرّس الذكي مخصص حصراً للمسارات التعليمية الموجودة في رُزمة: القدرات، التحصيلي، وSTEP إذا كان هذا المسار مفعّلاً في المنصة. لا يتحول إلى مساعد عام.

- مصادر المعرفة الوحيدة للإجابة التعليمية هي المدرسون والدورات والدروس والملفات وبنك الأسئلة المنشورة والمصرح بها داخل رُزمة.
- لا يخترع أسماء مدرسين أو دورات أو ملفات أو يوصي بمصادر غير موجودة في الموقع.
- لا يستخدم بحث الويب أو مصادر خارجية أو معلومات عامة لسد النقص.
- إذا لم يجد جواباً مدعوماً في محتوى رُزمة، يقول بوضوح إن المعلومة غير متوفرة في المواد الحالية، ويطلب من الطالب الرجوع إلى المدرس/المحتوى المعتمد أو إبلاغ الإدارة لإضافة المادة.
- أرفق مرجعاً داخلياً عند الإمكان: اسم المدرس، اسم الدورة/الملف، الدرس أو رقم الصفحة/المقطع. لا تخترع مرجعاً.
- يجب أن يكون لكل محتوى مفهرس معرّف مصدر وصلاحية وصول؛ لا يجوز للطالب الوصول إلى ملفات أو دورات غير مشمولة باشتراكه.

### ب. استقبال صور الطلاب

اسمح للطالب بإرفاق صورة داخل محادثة المدرّس، لكن الغرض التعليمي محصور في مسائل وأسئلة القدرات والتحصيلي (وSTEP فقط إذا اعتمد المالك ذلك).

- افحص الصورة أولاً لتحديد هل تحتوي على سؤال/مسألة/رسم أو جدول تعليمي مرتبط بأحد المسارات المعتمدة.
- إذا كانت صورة غير تعليمية أو خارج نطاق القدرات والتحصيلي، ارفض تحليلها بلطف واطلب صورة سؤال من المنهج المعتمد.
- لا تحاول وصف أو تحليل صور شخصية أو مستندات أو منتجات أو مواضيع عامة؛ لا تحتفظ بها كمحتوى تدريبي.
- إذا كانت الصورة غير واضحة أو ناقصة، اطلب صورة أوضح ولا تخمّن نص السؤال.
- استخرج نص السؤال والخيارات والرسومات ذات الصلة، ثم أجب اعتماداً على محتوى رُزمة المعتمد فقط. إذا لم تتوفر قاعدة كافية للحل في محتوى رُزمة، صرّح بذلك ولا تخترع.
- أظهر للطالب السؤال الذي تم فهمه قبل الحل عند وجود التباس، مع خيار تصحيح النص المستخرج.
- طبّق قيود نوع الملف والحجم وفحص الملفات، واحذف الملفات المؤقتة وفق سياسة احتفاظ واضحة، ولا تعرض الصور لمستخدمين آخرين.
- اختبر حالات الصور غير المدعومة، الصور المختلطة، السؤال المقتطع، الخيارات غير الظاهرة، والرسومات الهندسية.

### ج. السبورة الذكية

أضف سبورة تفاعلية حقيقية داخل المدرّس الذكي، وليست صورة ثابتة أو مجرد نص طويل.

- تعرض خطوات الحل تدريجياً كما يشرح مدرس بشري على السبورة.
- يدعم الرسم الحر بالقلم، المسح، التراجع/الإعادة، التحريك والتكبير، ومسح السبورة.
- يدعم كتابة المعادلات والجذور والكسور والرموز الرياضية بوضوح.
- يدعم رسم الأشكال الهندسية والمخططات والجداول والمحاور والرسوم البيانية المناسبة للمسألة.
- يستطيع المدرّس إنشاء رسومات توضيحية من خطوات الحل، مع تسميات وأسهم وقياسات عند الحاجة.
- تظهر الكتابة والرسم بالتتابع مع الشرح، وليس كل الحل دفعة واحدة؛ ويمكن للطالب إيقاف العرض أو الرجوع خطوة أو التقدم.
- يربط كل خطوة بشرح نصي موجز، ويبرز الجزء الذي يتحدث عنه المدرّس.
- اسمح للطالب بالرسم على السبورة أو إضافة ملاحظة دون تغيير الحل الأصلي، مع زر لإعادة السبورة إلى حل المدرّس.
- يجب أن تكون السبورة قابلة للاستخدام باللمس على الجوال والقلم/الفأرة على الكمبيوتر، وتدعم RTL.
- لا تدّع أن الرسم اليدوي حقيقي إن كان مولداً آلياً؛ اعرضه كرسوم متجهية/عناصر سبورة متحركة واضحة.
- اختر التقنية المتوافقة مع بنية المشروع الحالية بعد فحصها؛ لا تضف مكتبة كبيرة أو خدمة مدفوعة قبل تبرير الحاجة.
- احفظ نسخة من الحل/السبورة ضمن جلسة الطالب فقط إذا كان ذلك متوافقاً مع سياسة الخصوصية، ولا تجعل رسومات الطلاب عامة.

### د. أسلوب الرد

- حسّن System Instructions: جواب مباشر أولاً؛ شرح تدريجي حسب صعوبة السؤال وطلب الطالب؛ لا مقدمات طويلة ولا تمارين إضافية غير مطلوبة.
- أزرار متابعة: «اشرح أبسط»، «تلميح»، «حل خطوة بخطوة»، «اختبرني»، «سؤال أصعب».
- دعم عرض المعادلات والجذور والكسور بشكل صحيح في RTL.
- أضف Streaming إذا أمكن دون كسر البروتوكول الحالي.
- لا تجعل السرعة سبباً في إجابة غير متحققة؛ الدقة والالتزام بمصادر رُزمة أهم من الرد الفوري.
- لا ترسل كامل الملفات أو كل بنك الأسئلة في كل طلب؛ استرجع المقاطع ذات الصلة فقط.
- افصل الأسئلة الأصلية عن الأسئلة المولدة.
- مولّد الاختبارات يتيح للمشرف تحديد المسار والموضوع والعدد والصعوبة والوقت، ثم ينشئ مسودة للمراجعة قبل النشر.
- الاختبارات الرسمية يجب أن تعتمد أسئلة تمت مراجعتها؛ لا تنشر توليد AI تلقائياً دون موافقة.
- تعامل مع أخطاء OpenAI بدقة: insufficient_quota، rate_limit، invalid_api_key، model_not_found، timeout، server_error. اعرض للطالب رسالة مفهومة، وسجّل تفاصيل آمنة للأدمن.
- طبّق ميزانية مشتركة: تسجيل التكلفة الفعلية حسب الاستخدام، حجز تقديري قبل الطلب، تسوية بعده، سقف إنفاق داخلي، حدود عادلة لكل مستخدم، تنبيهات واحتياطي. لا تعتبر ميزانية التطبيق ضماناً ضد تجاوز حدود مزود API.
- لا تضع مفتاح API في الواجهة أو السجلات. حافظ على تخزين الأسرار الحالي.

## المرحلة 6 — لوحة المالك والإدارة

حوّل لوحة المالك إلى مركز قيادة:
- مؤشرات حقيقية للطلاب النشطين والاشتراكات والإيرادات واستخدام AI.
- تنبيهات للمدفوعات الفاشلة والاشتراكات المنتهية والملفات الفاشلة ومشكلات الخدمة.
- إدارة الطلاب مع البحث والتصفية وعرض سجل الطالب التعليمي والاشتراك والطلبات.
- إدارة المحتوى والأسئلة والاختبارات والدورات والمدرسين والمصادر.
- إدارة مكتبة معرفة المدرّس: الملفات، حالة الاستخراج والفهرسة، الأخطاء، المراجع، الصلاحيات، وإمكانية إعادة المعالجة/الأرشفة.
- مسودات ومعاينة قبل النشر وسجل تغييرات.
- تقارير قابلة للتصدير عند توفر دعم آمن.
- لا تضف أدوار موظفين جديدة في قاعدة البيانات دون تصميم صلاحيات واختبارات؛ قدم اقتراحاً منفصلاً إن احتاجت.

## المرحلة 7 — الحسابات والأمان والتجارة

راجع قبل التغيير:
- تسجيل الدخول والجلسات والصلاحيات.
- استعادة كلمة المرور والتحقق من البريد إن كانت ضمن نطاق التنفيذ.
- OAuth لا يضاف إلا بتدفق آمن وإعدادات callback صحيحة.
- حماية API من الوصول غير المصرح وCSRF/XSS/SQL injection ورفع الملفات الخطرة.
- التحقق من الدفع webhook server-side ومنع تكرار معالجة الحدث.
- صلاحيات اشتراكات المحتوى المدفوع.
- سجل تدقيق للعمليات الإدارية الحساسة.
- لا تغير مزود الدفع أو إعداداته الحية ولا تنفذ دفعات حقيقية للاختبار.

## المرحلة 8 — التنظيف والأداء والاستقرار

- احذف الملفات/المكونات غير المستخدمة فقط بعد إثبات عدم استخدامها بالبحث والاختبارات.
- حسّن تحميل الصفحات والصور والملفات وتقسيم الحزم.
- راجع استعلامات قاعدة البيانات والفهارس.
- راجع حدود رفع الملفات وتخزين الفيديو والتخزين الدائم.
- قيّم SQLite تحت الاستخدام المتوقع؛ لا تنقل إلى PostgreSQL في هذه المهمة دون قرار منفصل ومخطط ترحيل معتمد.
- أضف logging آمن وhealth checks ومراقبة أخطاء لا تكشف بيانات حساسة.

## خطة الاختبارات المطلوبة

قبل طلب المراجعة:
1. اختبارات unit لكل منطق تمت مراجعته.
2. اختبارات API للصلاحيات والاشتراكات والاختبارات وAI.
3. اختبارات regression للحسابات والاشتراكات والنتائج وسجل التقدم.
4. اختبارات migration على نسخة قاعدة بيانات اختبارية.
5. اختبارات بناء production وlint/typecheck إن كانت معرفة.
6. اختبارات واجهة أساسية: زائر، طالب جديد، طالب مشترك، مالك.
7. اختبارات responsive على عرض جوال ولوحي وسطح مكتب.
8. اختبارات حالات فشل الشبكة وOpenAI والدفع ورفع الملفات.
9. اختبارات الصور: سؤال قدرات/تحصيلي مقبول؛ صورة خارج المجال مرفوضة؛ صورة غير واضحة تطلب إعادة رفع؛ لا تخمين عند نقص المعطيات.
10. اختبارات السبورة: رسم المعادلات والأشكال والمحاور، تتابع الخطوات، undo/redo، لمس الجوال، RTL، وإمكانية إعادة الضبط.
11. اختبارات مصدر المعرفة: الإجابة من ملف/مدرس موجود فقط؛ سؤال غير مغطى لا يجيب عنه من معرفة عامة ولا يخترع مصدراً.
12. فحص عدم تسريب الأسرار وعدم تضمين بيانات شخصية.
13. اكتب تقريراً يوضح ما نجح وما فشل وما لم يتم اختباره.

## معايير قبول المشروع

- لا فقد للحسابات أو الاشتراكات أو النتائج أو تقدم الطلاب.
- كل الصفحات الأساسية تعمل على الجوال والكمبيوتر.
- كل زر ظاهر يؤدي وظيفة حقيقية؛ لا أزرار وهمية.
- لا توجد روابط مكسورة أو أخطاء Console/Server معروفة غير موثقة.
- يستطيع الطالب الجديد فهم نقطة البداية دون شرح خارجي.
- يستطيع المالك إدارة الطلاب والمحتوى والاشتراكات بسهولة.
- يستطيع المالك رفع ملف ومراجعة أسئلته قبل النشر.
- المدرّس يجيب باختصار مناسب أولاً ويشرح عند الطلب.
- المدرّس لا يستخدم إلا محتوى رُزمة والمدرسين والملفات المصرح بها.
- الصور خارج مجال القدرات والتحصيلي ترفض بأدب، والصور غير الواضحة لا تُحل بالتخمين.
- السبورة الذكية تعرض حلاً مرسوماً ومتدرجاً وقابلاً للتفاعل على الجوال والكمبيوتر.
- ميزانية AI واضحة ومراقبة.
- كل الاختبارات موثقة بنتائج حقيقية.
- المالك عاين واعتمد الواجهات الجديدة قبل التنفيذ الشامل وقبل أي نشر.
