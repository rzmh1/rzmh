# تشغيل رُزمة على Northflank

هذه إعدادات مقترحة للمراجعة، ولم تُطبّق على خدمة إنتاج. اختُبرت صورة Docker محليًا على Node.js 24 بمنفذ مخصص وقاعدة مؤقتة.

## الخدمة والبناء

- أنشئ خدمة من المستودع باستخدام `Dockerfile` في الجذر وسياق البناء `.`. البناء يثبّت اعتماديات التطوير لبناء CodeMirror ثم يحتفظ باعتماديات الإنتاج فقط في صورة التشغيل.
- أمر التشغيل الافتراضي `node server/index.mjs`؛ للتشغيل من المصدر بعد `npm ci` استخدم `npm run build` ثم `npm start`.
- شغّل **نسخة واحدة فقط**. SQLite ووسائط local تحتاج القرص نفسه وكاتبًا واحدًا؛ لا تضبط autoscaling متعدد النسخ أو حاويتين تكتبان قاعدة واحدة بالتزامن. راجع سلوك استبدال الحاويات وتركيب القرص لدى Northflank قبل أي rollout.
- اختر منفذ HTTP داخليًا، مثل `3000`، واجعل `PORT` مطابقًا. الخادم يستمع على `HOST=0.0.0.0`، والصورة تحترم تغيير `PORT`.
- عيّن فحص HTTP إلى `GET /api/health` على المنفذ الداخلي دون مصادقة. الصورة تتضمن أيضًا Docker HEALTHCHECK؛ اضبط فحوص Northflank صراحةً.
- أنهِ HTTPS عند مدخل المنصة، مع فترة إنهاء لا تقل عن 30 ثانية. يعالج الخادم SIGTERM/SIGINT ويصرف الطلبات وتحويل الفيديو الجاري حتى 25 ثانية. التحويل الأطول الذي يقطع عند إعادة التشغيل يحتفظ بسجل الملف ويظهر فاشلًا وفق السلوك السابق؛ يحتاج إعادة رفع.

## البيانات والأسرار

للتثبيت الجديد فقط، اركب قرصًا دائمًا قابلًا للكتابة للمستخدم `node` (UID/GID 1000) على `/app/runtime` واضبط `DATA_DIR=/app/runtime`. القرص يضم SQLite وWAL والوسائط المحلية والملفات المؤقتة والنسخ. التخزين السحابي لا يغني عن القرص الدائم لقاعدة SQLite.

**عند تحديث خدمة قائمة، احتفظ بمسار DATA_DIR وتركيب القرص الحاليين وبـ APP_KEY نفسه. لا تغيّر المسار إلى المثال أعلاه إن كان لديك مسار آخر، ولا تنشئ قرصًا فارغًا بديلًا.** خذ نسخة قاعدة ووسائط خارج الخدمة أولًا، وطبّق [دليل الترقية](UPGRADE-3.md) على نسخة معزولة من البيانات.

أدخل القيم في متغيرات الخدمة ومخزن أسرار Northflank؛ لا تضف `.env` إلى Git أو الصورة:

| المتغير | القيمة المطلوبة |
| --- | --- |
| `NODE_ENV` | `production` |
| `APP_ORIGIN` | أصل HTTPS الفعلي فقط، بلا مسار أو `/` أخيرة |
| `APP_KEY` | مفتاح Base64 من 32 بايت؛ احتفظ بالمفتاح القائم عند التحديث |
| `PORT`, `HOST` | منفذ HTTP المعلن و`0.0.0.0` |
| `DATA_DIR` | مسار القرص الدائم الفعلي |
| `STORAGE_DRIVER` | `local` أو `s3` |
| `S3_*` | إعدادات حاوية خاصة عند استخدام S3/R2، وفق [التكاملات](INTEGRATIONS.md) |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `OPENAI_API_KEY` | اختيارية؛ يمكن أيضًا حفظها مشفرة من لوحة المالك |

لا تفعّل `TRUST_PROXY=1` إلا بعد التأكد أن المدخل الموثوق يعيد تعيين `X-Real-IP` ولا يقبلها من العميل. التنفيذ الحالي يعتمد هذا الرأس، وليس X-Forwarded-For؛ تحقق من إعداد المدخل كي تعمل حدود الدخول لكل عميل. لا تغيّر الثقة تلقائيًا.

FFmpeg وFFprobe مدمجان في الصورة. وفّر ذاكرة وCPU ومساحة مؤقتة كافية للفيديوهات، وحد رفع/مهلة HTTP تناسب `MAX_UPLOAD_BYTES` (الافتراضي 2 GiB). التحويل متسلسل داخل العملية.

## القبول قبل الإطلاق

1. تأكد أن القرص والمفتاح والدومين الحاليين صحيحون، ثم شغّل فحص الصحة.
2. للتثبيت الجديد فقط أنشئ المالك من terminal الخدمة: `node scripts/setup-admin.mjs`. لا تعِد إنشاء مالك قائم لمجرد التحديث.
3. اختبر دخول المالك والطالب، رفض صلاحيات الإدارة للطالب، المعاينة والدروس والرفع والجدولة.
4. أعد تشغيل خدمة الاختبار وتأكد من بقاء الحسابات والاشتراكات والوسائط. اختبر الاستعادة من نسخة مستقلة.
5. اختبر Stripe وWebhook وS3/R2 وOpenAI بمفاتيح حسابك في بيئة اختبار قبل Live. لا توجد مفاتيح متاحة في هذه المهمة ولا ادعاء باتصال خارجي ناجح.
6. اختبر Safari/iOS وAndroid على أجهزة فعلية. اختبارات Chromium المكتبية وبعرض الجوال لا تثبت توافق محركات المتصفح الأخرى.
